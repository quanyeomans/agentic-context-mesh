# Upgrading to v2026.5.28a1 — streaming bronze (default + only model)

Bronze persistence shifts from on-disk raw blobs to metadata-only rows.
The v2026.5.27a2 dogfood showed 112 GB of bronze accumulating against 8,783
SharePoint items; on the same corpus under streaming bronze, that drops to
the kB scale.

## Operator-facing changes

### 1. Remove `bronze_mode` from your config

If your `kairix.config.yaml` has any of these forms, delete the line:

```yaml
connectors:
  - name: sharepoint
    bronze_mode: filesystem   # ← remove
    extractor_chain: [markitdown, pdf_fallback, ocr]
```

```yaml
connectors:
  - name: sharepoint
    bronze_mode: streaming    # ← remove (it's now the only mode)
    extractor_chain: [markitdown, pdf_fallback, ocr]
```

The worker logs a per-connector warning at sync time and refuses to run that connector until the field is removed:

```
worker: connector sharepoint failed — 'bronze_mode' config field is no
longer accepted — streaming bronze is the only persistence model.
fix: remove the 'bronze_mode' line from your kairix.config.yaml.
next: see docs/architecture/streaming-bronze-plan.md § 7
```

### 2. Existing on-disk bronze blobs become unused

If your deploy ran v2026.5.27 or earlier and accumulated bronze blobs on disk, those blobs are no longer touched by the worker. Bug D `kairix worker reextract` still reads them for pre-Phase-7 dead-letter rows (so recovery works for items that were dead-lettered before the upgrade), but no new writes land on disk.

Once you've run reextract against any remaining pre-upgrade dead-letter rows, clean up the disk:

```bash
docker compose exec kairix kairix worker reextract --source-name <name> --json
# Inspect the result; if recovered + skipped_source_unavailable accounts for
# every dead_letter row, the bronze blobs are no longer needed.

# Then on the VM:
sudo rm -rf /var/lib/kairix-runtime/bronze/
```

### 3. Re-extract has a new outcome counter

The `kairix worker reextract --json` envelope gained `skipped_source_unavailable` in v2026.5.27a2 (Phase 6 of the streaming-bronze rollout). After this upgrade, that counter increments whenever a streaming-bronze row's source file is deleted between original fetch and re-extract.

```json
{
  "source_name": "sharepoint",
  "recovered": 8500,
  "still_failing": 35,
  "skipped_no_bronze": 2,
  "skipped_no_connector": 0,
  "skipped_source_unavailable": 12,
  "dry_run": false
}
```

Operators monitoring dead-letter recovery should add the new counter to their dashboards.

## Why this shipped

The v2026.5.27a2 dogfood revealed that a SharePoint corpus of 8,783 items consumed 112 GB of bronze. Production deployments can't assume that scale of spare disk; a 50,000-item corpus would project to ~650 GB; a 200,000-item corpus to 2.5 TB. The bronze-as-disk model was structurally incompatible with the kind of corpora kairix targets.

Bronze.read was only ever called by the re-extract recovery path (Bug D). The main pipeline used the in-memory bytes from `connector.fetch` directly. Streaming bronze drops the persistent-blob layer entirely and routes re-extract through `connector.fetch(item_id)` — re-fetch from source rather than re-read from disk. The trade-off: re-extract becomes slower (and source-rate-limit aware) but disk usage drops by ~6,000x.

Full architectural rationale: [`docs/architecture/streaming-bronze-plan.md`](../architecture/streaming-bronze-plan.md).

## Rollback

```bash
KAIRIX_IMAGE_TAG=2026.5.27a2 docker compose pull
KAIRIX_IMAGE_TAG=2026.5.27a2 docker compose up -d --force-recreate
```

The schema change (added `content_hash` column, no removals) is forward-compatible — rolling back to v2026.5.27a2 works because the column is nullable and unused by older code. The deleted `FilesystemBronzeStore` class lives in git history.
