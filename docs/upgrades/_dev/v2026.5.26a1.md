## Upgrading to kairix v2026.5.26a1 (alpha)

Three bug fixes that change how kairix handles its rough edges — none of them require a config change.

The big one is `ConnectorPipeline` chunked commits (#321) — long SharePoint backfills used to leak thousands of orphan files on every worker restart because the whole batch ran as one SQLite transaction. The pipeline now commits every 50 items by default; a failure loses at most one chunk's work.

The second is the MCP cold-start handoff (#320) — agents used to see the opaque string `"fetch failed"` for the first 7-30s after a kairix restart because the HTTP port wasn't bound during the warm sequence. Now uvicorn binds first, warm runs in the background, and the `ColdStartMiddleware` returns a structured `ColdStart` envelope that tells agents exactly how to retry.

The third is `tenacity` adoption for the `dex_crm` HTTP-retry loop — the reference shape future connectors should copy.

If you're not running connectors against external sources yet, this upgrade is a straight pull with no behaviour change.

## What this release covers

- **Per-chunk commit in `ConnectorPipeline` (#321).** Every `chunk_size` items processed inside a batch trigger a `cursor advance + DB commit`. A failure mid-chunk rolls back only that chunk; earlier chunks stay committed and the cursor advances per chunk so the next batch resumes after the last committed item. Default `chunk_size=50` matches SharePoint backfill cadence (~1 item/sec → one commit every ~50s). Regression-locked by two characterization tests in `tests/integration/test_connector_pipeline_long_batch_durability.py`.

- **MCP cold-start: uvicorn binds before warm + positive-action affordance envelope (#320).** Warm now runs in a daemon thread; uvicorn binds the HTTP port immediately. During the warm window (7-30s on cold start) the existing `ColdStartMiddleware` returns HTTP 503 + a `ColdStart` envelope so agents see a structured retryable status instead of the OS-level "fetch failed" they used to get on connection-refused. The envelope's `agent_instruction` was also rewritten to lead with positive `next:` / `fix:` actions instead of stacking "do not X, do not Y" prohibitions — per the `feedback_agent_prompts_positive_assertion` affordance pattern.

- **`dex_crm` HTTP retry refactored to use `tenacity` (post-OSS-evaluation cleanup).** Replaces ~30 LoC of hand-rolled `while True` retry with `tenacity.Retrying(retry_if_result, wait_exponential, stop_after_attempt)`. Same observable behaviour (12 existing dex_crm tests pass unchanged). `tenacity` is now a base dependency (one dep, no transitives); future connectors needing HTTP retry should follow this pattern.

- **OSS connector-library evaluation outcome (`docs/architecture/connector-oss-library-evaluation.md`).** Four candidates (dlt, Airbyte Python CDK, Meltano Singer SDK, PyAirbyte) evaluated in parallel against hard requirements. All four rejected on raw-binary-blob fit. Documented recommendation: stay homegrown + adopt `tenacity` (this release). The evaluation methodology is the reference shape for future "should we adopt OSS library X" decisions.

- **Operator doc correction (`docs/operations/OPERATIONS.md` §5.6).** The previous v2026.5.25 guidance said "data on the data disk." That assumed a deploy shape where the data disk is the largest one — the production instance has the opposite shape (256 GB OS disk, 64 GB data disk). The revised guidance is "kairix runtime on whichever disk is largest" with a `df -h` check.

## Before the upgrade

No baseline change required. The chunking change is purely internal — same Protocol surface, same API.

If your VM's kairix runtime is bind-mounted to a small disk and you've been hitting disk-full issues, take the opportunity to move it during this upgrade — see the revised `OPERATIONS.md` §5.6.

## What to verify

```bash
# Look for a connector-sync log line — should show batch counts.
# With chunked commits, you'll see multiple commit boundaries per batch
# instead of a single one at the end.
docker compose logs --tail=200 kairix-worker | grep -E "connector_sync|batch"

# After a connector cycle, bronze_records count should equal on-disk
# file count for that source (or be off by at most chunk_size if a
# chunk failed mid-stream — the #318 orphan reaper cleans that up).
docker compose exec kairix-worker python3 -c "
import sqlite3, os
db = sqlite3.connect('/data/kairix/index.sqlite')
for src in ('obsidian', 'sharepoint'):
    rows = db.execute('SELECT count(*) FROM bronze_records WHERE source_name=?', (src,)).fetchone()[0]
    d = f'/data/kairix/bronze/{src}'
    if os.path.isdir(d):
        files = sum(1 for p in os.listdir(d) if os.path.isdir(f'{d}/{p}') for f in os.listdir(f'{d}/{p}') if os.path.isfile(f'{d}/{p}/{f}'))
    else:
        files = 0
    print(f'{src}: bronze_records={rows} on_disk={files} orphans={files - rows}')
"
```

Healthy output: orphan count ≤ `chunk_size` (50 by default) per source. If non-zero, the maintenance loop's bronze-orphan stage (#318) reaps them on the next tick.

## Tuning

Override `chunk_size` via the constructor if you want a different commit granularity:

```python
# Smaller chunks = faster recovery from failure, more commit overhead.
# Larger chunks = better throughput, more orphans on failure.
pipeline = ConnectorPipeline(..., chunk_size=20)
```

In practice the 50-item default is right for HTTP-bound connectors (SharePoint, Slack, GitHub). For local connectors (Obsidian) the chunking is invisible because the batch usually finishes faster than the chunk boundary.

## Rollback

```bash
KAIRIX_IMAGE_TAG=2026.5.25a1 docker compose pull
KAIRIX_IMAGE_TAG=2026.5.25a1 docker compose up -d --force-recreate
```

The chunking change is purely additive at the API surface — rolling back doesn't lose committed data. You revert to the pre-#321 single-transaction behaviour.
