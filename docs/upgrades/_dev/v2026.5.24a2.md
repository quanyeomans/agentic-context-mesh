# Upgrading to kairix v2026.5.24a2 (alpha)

This is the second alpha in the v2026.5.24 series. It adds three new connectors (Slack, GitHub, Notion), a per-connector topology pilot for the existing connectors that didn't have one yet (Dex CRM, M365 email headers, M365 calendar, SharePoint), and a background maintenance loop for orphan-vector cleanup. Every new behaviour is default-off — pulling the alpha doesn't change anything until you flip a flag.

If you're on `v2026.5.24a1`, you can pull this version directly. If you're on a stable release earlier than `v2026.5.24a1`, read [v2026.5.24a1.md](v2026.5.24a1.md) first — the topology operator-config surface introduced there is what these new connector pilots build on.

## What this release covers

- **Slack connector ships behind `connector_slack`.** Pulls public, private, and direct-message channels via the Web API plus a Socket Mode listener for live events. Sensitivity is set per channel kind (public → internal, private → confidential, DM → personal) so the F39 routing applies without operator config. Token rotation under the per-cc_pair lock; reconnect-with-jitter on disconnect.
- **GitHub connector ships behind `connector_github`.** Pulls code, issues, and pull requests via REST + GraphQL with a webhook listener for push / issues / pull_request / installation_repositories events. Personal-access-token or App-installation credentials both work — the connector picks whichever you provided. Abuse-detection backoff is automatic when GitHub returns secondary rate-limit responses.
- **Notion connector ships behind `connector_notion`.** Pulls workspace pages plus database rows via the public API, renders block trees to Markdown, then dispatches the Markdown to the existing kairix extractor registry. The included `passthrough` and `markitdown` extractors both handle the output without any extra config.
- **Per-connector topology pilots ship for the existing connector fleet.** Five new flags — `topology_dex_crm`, `topology_m365_email_headers`, `topology_m365_calendar`, `topology_sharepoint`, `topology_slack`, `topology_github`, `topology_notion` — each emit one Container per source-side unit (tenant, mailbox, calendar, drive, channel, repository, workspace page tree) with its own delta cursor instead of one connector-wide cursor. Default off; mirrors the `topology_obsidian` pilot shape landed in a1.
- **Maintenance loop ships behind `maintenance_loop`.** When the flag is on, the worker fires a periodic tick (default every 24 hours, tunable via `KAIRIX_MAINTENANCE_INTERVAL_S`) that prunes orphaned `content_vectors` rows into a soft-delete table with a 7-day retention window before hard-deleting. Replaces the reactive KFEAT-020 preflight check — orphan vectors get cleaned up in the background instead of blocking the next ingest. Surfaces: `kairix worker maintenance` (one-shot tick), `kairix worker preflight --auto-heal` (now also prunes), `kairix features status --maintenance` (operator visibility).

One new `kairix onboard check` lands alongside, gated by the same flag:

- `maintenance_loop_ticking` — when the flag is ON, confirms the worker has fired a tick within the expected interval. When OFF, reports `ok=true` with `"skipped — maintenance_loop flag is OFF"`.

A fresh install sees 15 checks pass (was 14), no operator action required.

## Before the upgrade

1. **Back up your data volumes.** Docker: `docker run --rm -v kairix-data:/data -v "$PWD":/backup busybox tar czf /backup/kairix-data-pre-v2026.5.24a2.tgz /data`. Pip: copy `~/.cache/kairix/index.sqlite` and your document root.
2. **Snapshot your eval baseline.** Run `kairix benchmark run reflib --out benchmark-results/pre-v2026.5.24a2.json`. After the upgrade, run again and diff with `--baseline benchmark-results/pre-v2026.5.24a2.json`.
3. **Note the current `kairix onboard check --json` envelope.** New deployments should expect one new check entry (`maintenance_loop_ticking`, reporting `skipped` with the flag off).

## After the upgrade — opting into the new connectors

Everything below is OPTIONAL. Skip if you're not running the alpha.

### Slack

**Required privileges** — grant these in Slack admin → Apps → your app → **OAuth & Permissions** → Bot Token Scopes:

| Scope | Why |
|---|---|
| `channels:history` | Read messages from public channels |
| `channels:read` | List public channels + members |
| `groups:history` | Read messages from private channels the bot is in |
| `im:history` | Read direct messages with the bot |
| `mpim:history` | Read multi-person DMs the bot is in |
| `users:read` | Resolve user ids to display names |
| `files:read` | Fetch file metadata for sensitivity routing |
| `chat:write` | Generate stable message permalinks (read path) |

For Socket Mode live events, also create an app-level token under **App-Level Tokens** with the `connections:write` scope. Without Socket Mode the connector falls back to polling.

After granting, **invite the bot to each channel you want indexed** — `/invite @your-bot-name` in the channel. The bot can't read history from a channel it isn't a member of.

Provision the secrets via whichever path your deployment uses. See [`docs/getting-started/agent-driven-setup.md §3 "Secrets shape"`](../getting-started/agent-driven-setup.md#3-secrets-shape) for the canonical KV / bundle / per-file recipe.

| Logical name (KV secret name) | Env-var form (bundle file) | Required? |
|---|---|---|
| `connector-slack-bot-token` | `CONNECTOR_SLACK_BOT_TOKEN` | yes; `xoxb-...` |
| `connector-slack-app-token` | `CONNECTOR_SLACK_APP_TOKEN` | only for Socket Mode live events; `xapp-...` |

Add a connector entry in your `kairix.config.yaml` under `topology.connectors:` and turn the flag on:

```yaml
topology:
  connectors:
    - id: slack-workspace-conn
      kind: slack
      name: "Slack — your-team workspace"
      default_sensitivity: internal
      connector_specific_config:
        workspace_id: "T01ABCDEF"            # your workspace id (slack admin → about)

features:
  connector_slack: true
  topology_slack: true                    # optional — per-channel containers
```

Then `kairix worker apply-config` to materialise the cc_pair row.

### GitHub

**Required privileges** — these are the same whether you use a personal access token or a GitHub App. Grant in GitHub.com → Settings → Developer settings → (Personal access tokens OR GitHub Apps → your app → Permissions and events) → Repository permissions:

| Permission | Access level | Why |
|---|---|---|
| Contents | Read | Walk repo trees + fetch blob content |
| Issues | Read | Pull issues + their bodies |
| Pull requests | Read | Pull PR metadata + diffs |
| Metadata | Read | Always granted; required for repo enumeration |

For the App-installation path, also configure these **webhook events** under the app's "Subscribe to events" section so the live listener gets fired:

- `push` — commits land
- `issues` — issue created / updated / closed
- `pull_request` — PR opened / updated / merged / closed
- `installation_repositories` — app added to / removed from a repo

Then **install the app on the repos you want indexed** (GitHub.com → your app → Install → choose "Only select repositories"). The connector enumerates only the repos the installation has been granted.

For the PAT path, the token automatically covers every repo the user owns or is a member of with the granted scope; no per-repo install step needed.

Pick one credential path and provision via the resolver in [`docs/getting-started/agent-driven-setup.md §3 "Secrets shape"`](../getting-started/agent-driven-setup.md#3-secrets-shape) (KV / bundle / per-file). The connector picks whichever resolved.

PAT path:

| Logical name | Env-var form | Value |
|---|---|---|
| `connector-github-personal-access-token` | `CONNECTOR_GITHUB_PERSONAL_ACCESS_TOKEN` | `ghp_...` |
| `connector-github-webhook-secret` | `CONNECTOR_GITHUB_WEBHOOK_SECRET` | random 32-byte hex (only if you want the webhook listener) |

App-installation path:

| Logical name | Env-var form | Value |
|---|---|---|
| `connector-github-app-id` | `CONNECTOR_GITHUB_APP_ID` | numeric app id |
| `connector-github-installation-id` | `CONNECTOR_GITHUB_INSTALLATION_ID` | numeric installation id |
| `connector-github-app-private-key` | `CONNECTOR_GITHUB_APP_PRIVATE_KEY` | PEM contents on one line |
| `connector-github-webhook-secret` | `CONNECTOR_GITHUB_WEBHOOK_SECRET` | random 32-byte hex |

Then in `kairix.config.yaml`:

```yaml
topology:
  connectors:
    - id: github-org-conn
      kind: github
      name: "GitHub — example-org"
      default_sensitivity: client-confidential   # safe default for private repos
      connector_specific_config: {}              # no extra config needed at the connector level

features:
  connector_github: true
  topology_github: true                       # optional — per-repo containers
```

Point your GitHub webhook at your kairix host: `https://your-kairix-host/connectors/github/webhook`. The connector validates the HMAC signature on every delivery and deduplicates replays by delivery id.

### Notion

**Required privileges** — create an internal integration in your workspace settings:

1. Notion → Settings & members → **Integrations** → "Develop or manage integrations" → New integration
2. Under **Capabilities**, enable **Read content**. Leave the other two ("Update content", "Insert content") off — the kairix connector is read-only.
3. Copy the **Internal Integration Token** (starts with `secret_`) — this is `CONNECTOR_NOTION_INTEGRATION_TOKEN`.

Notion gates access per-page, not per-scope. Even with the token set, the connector can't read anything until each page or database is **explicitly shared with the integration**:

- For an individual page or database: open it → **Share** (top right) → search for the integration by name → Invite (read access).
- For a whole section of your workspace: share the parent page once — child pages inherit.

The connector calls `POST /v1/search` (filtered to pages + databases), `POST /v1/databases/{id}/query` (for database rows), and `GET /v1/blocks/{id}/children` (for the block tree). All read-only; no write capability is needed or granted.

Provision the secret via the resolver in [`docs/getting-started/agent-driven-setup.md §3 "Secrets shape"`](../getting-started/agent-driven-setup.md#3-secrets-shape):

| Logical name | Env-var form | Value |
|---|---|---|
| `connector-notion-token` | `CONNECTOR_NOTION_TOKEN` | `secret_...` integration token |

Then:

```yaml
topology:
  connectors:
    - id: notion-workspace-conn
      kind: notion
      name: "Notion — your-team workspace"
      default_sensitivity: internal
      connector_specific_config: {}              # the integration's auth scope picks the workspace

features:
  connector_notion: true
  topology_notion: true                       # optional — per-page-tree containers
```

Then share the pages or databases you want indexed with the integration (Notion → page → share → invite your integration by name).

### Maintenance loop

If you've ever hit a "ghost search hit" (a result pointing at a document you deleted), turning this on prunes the offending vectors in the background instead of waiting for the next preflight check:

```yaml
features:
  maintenance_loop: true
```

Optional: `KAIRIX_MAINTENANCE_INTERVAL_S=86400` (24h default). Confirm the loop is firing:

```bash
kairix features status --maintenance
# shows: enabled=true, last_tick_at=2026-05-24T07:13:15+10:00, orphans_pruned_total=N
```

## Expected drift

- **reflib NDCG@10 may move ±0.02** if you flipped any of the new topology per-connector flags on a real corpus. The per-source containers change how cross-collection ranking weights — re-run `kairix benchmark run` after a full embed pass to settle the new baseline. Closes when KFEAT-015 ships per-collection ranker calibration.
- **First sync after flipping each `topology_<connector>` flag re-walks the source** to emit the per-source containers. Subsequent syncs ride the delta cursors and are fast.
- **First maintenance tick can take longer** than subsequent ticks if your index has accumulated months of orphan vectors. Watch the `orphans_pruned` counter — once it returns to single digits the index has settled.

## Rolling back

Every new behaviour is reversible by removing its flag entry from `features:` (or unsetting the matching `KAIRIX_FEATURE_*` env var). The new `topology.connectors` entries stay parseable when their flag is off — they become inert. No data migration is required.

If you've flipped any `topology_<connector>` flag, the first sync after the flip re-walks the source to register per-source containers. Flipping the flag back off returns the connector to the single-cursor shim. The container rows stay in the topology tables as read-only inputs to the runtime; no cleanup needed.

If you've flipped `maintenance_loop`, soft-deleted rows in `content_vectors_pruned` are retained for 7 days before hard-delete. Flipping the flag back off stops new pruning; rows already in the soft-delete table age out on the existing retention schedule.

## Things that haven't changed

- The legacy `collections:` + `agents:` blocks. Operators using them continue to work.
- The provider plugin selector (`provider:`). Same shape, same plugins.
- MCP tool names + JSON schemas. The 12 tools shipped in v2026.5.18 (plus `tool_features_status` from v2026.5.24a1) are unchanged.
- Authentication. kairix continues to have no built-in auth.
