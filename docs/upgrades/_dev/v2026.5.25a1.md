## Upgrading to kairix v2026.5.25a1 (alpha)

This alpha bundles five fixes from the 2026-05-24 SharePoint production run incident, where a real corpus revealed five gaps in how kairix manages disk, bronze storage, maintenance scheduling, and operator-visible version state. None of the changes alter behaviour by default — flags ship OFF, env-vars stay at safe defaults — but every fix tightens the floor for what an operator can rely on without being a kairix expert.

If you're not running connectors against external sources yet, the only thing to verify after upgrade is that `kairix onboard check` still reports 15/15.

## What this release covers

- **`/tmp` on tmpfs by default (#317).** Both `kairix` and `kairix-worker` ship a 2 GB tmpfs `/tmp` mount in the canonical `docker-compose.yml` and `docker-compose.example.yml`. Connector binary fetches (SharePoint downloads, markitdown PDF / PPTX conversions) stay bounded by RAM instead of spilling onto the host root filesystem. Operators with custom override files inherit the same default unless they explicitly remove it.

- **Bronze orphan reaper (#318).** The bronze module documented "post-fsync-pre-commit orphans" as "harmless garbage that can be GC'd by a sweeper" but never shipped the sweeper. The 2026-05-24 production instance ended up with 36 GB of orphan blobs on the SharePoint tree because a sequence of partial fetches landed on disk but never finished registering. A new maintenance scheduler stage walks every connector's bronze tree on every tick and deletes any file with no `bronze_records` row. 5-minute grace period skips files mid-fsync. Always on once the `maintenance_loop` flag is ON (this stage piggybacks on the same tick cadence).

- **Bronze TTL garbage collection (#316, default OFF).** New `bronze_ttl_gc` feature flag. When ON, the maintenance scheduler deletes bronze raw blobs (and their `bronze_records` rows) older than `KAIRIX_BRONZE_TTL_DAYS` (default 7). Bounds long-term bronze growth — without this, correctly-registered blobs accumulate forever as the corpus churns. Default OFF until each deploy validates that re-fetch from source is reliable for every configured connector.

- **`connector_sync` decoupled from the embed-noop maintenance gate (#312).** When the local vault produced enough no-op embed cycles in a row, the worker was suppressing every maintenance task — including `connector_sync` — until the next embed found work. A quiet local vault was incorrectly assumed to mean quiet upstream sources, so SharePoint / Slack / GitHub / Notion sync froze for the entire duration of any local idle period. `connector_sync` now runs on its own interval regardless of the embed-noop streak. Local-only tasks (`entity_seed`, `health_check`, `wikilinks_inject`) still gate as before. Operators with `KAIRIX_MAINTENANCE_SKIP_NOOP_THRESHOLD=999999` set as a band-aid can drop the env-var after this upgrade.

- **Sticky `KAIRIX_IMAGE_TAG` to prevent version-drift (#313).** The alpha-deploy webhook now writes `KAIRIX_IMAGE_TAG=<version>` to `/opt/kairix/app/.env` between the secrets refresh and the docker compose pull. Subsequent ad-hoc `docker compose up -d --force-recreate kairix-worker` commands on the VM now interpolate the same tag instead of silently falling back to `:latest` (which can be months behind, as happened during v2026.5.24 production). Other `.env` vars are preserved; the write is idempotent.

## Before the upgrade

No baseline change required.

- **If `KAIRIX_MAINTENANCE_SKIP_NOOP_THRESHOLD=999999` is set as a band-aid for the connector_sync suppression, leave it in place during the upgrade.** After confirming `kairix onboard check` reports 15/15 and one `maintenance_tick_completed` log line shows up post-upgrade, you can drop the env-var.

- **If you have an existing `kairix-data` Docker named volume**, your bronze tree may be on the OS disk, not on a data disk. This release does not migrate volumes for you, but the new operator guidance in [`docs/operations/OPERATIONS.md` §5.6](../operations/OPERATIONS.md) walks through the bind-mount layout that survives a backfill. The orphan reaper (#318) and TTL GC (#316) work either way; they just don't make the OS disk magically grow.

### Docker

```bash
docker compose pull
docker compose up -d
docker compose exec kairix kairix --version            # confirm v2026.5.25a1
docker compose exec kairix kairix onboard check        # confirm 15/15 pass
```

### Pip

```bash
pip install --upgrade "kairix[agents]==2026.5.25a1"

```

## After the upgrade — optional cleanup

### Drop the maintenance-skip band-aid (if you set one)

```bash
# Edit docker-compose.override.yml — remove the env-var line:
# - KAIRIX_MAINTENANCE_SKIP_NOOP_THRESHOLD=999999

docker compose up -d --force-recreate kairix-worker
# (You don't need to pass KAIRIX_IMAGE_TAG inline any more — #313 wrote it to .env.)
```

### Turn on bronze TTL GC

```yaml
# kairix.config.yaml
features:
  bronze_ttl_gc: true
```

```bash
# Optional — override the 7-day default:
echo 'KAIRIX_BRONZE_TTL_DAYS=14' >> /opt/kairix/app/.env

docker compose up -d --force-recreate kairix-worker
docker compose logs kairix-worker | grep bronze_ttl_gc_deleted   # first tick reports the count
```

### Move kairix data onto a dedicated data disk (if it isn't already)

See [`docs/operations/OPERATIONS.md` §5.6 "Data on a data disk, not the OS disk"](../operations/OPERATIONS.md). The shipped compose tmpfs (#317) keeps `/tmp` off the OS disk but doesn't move `kairix-data` or `neo4j-data`. For deployments holding more than a few hundred MB of bronze, bind-mount to `/data/kairix/` rather than letting Docker default to `/var/lib/docker/volumes/`.

## What to verify

Run after upgrade:

```bash
# 1. onboard checks still 15/15
docker compose exec kairix kairix onboard check

# 2. maintenance tick completes — should log bronze_orphans_reaped and bronze_ttl_gc_deleted
docker compose logs --tail=200 kairix-worker | grep maintenance_tick_completed

# 3. connector_sync runs even if local embeds are no-op'ing
docker compose logs --tail=200 kairix-worker | grep -E "connector_sync (started|finished)"

# 4. .env carries the image tag now
grep KAIRIX_IMAGE_TAG /opt/kairix/app/.env
```

A healthy first tick after upgrade looks like:

```
event=maintenance_tick_completed pid=... orphans_pruned=0 pruned_table_size=0 usearch_rebuilt=False
fts_orphans_healed=0 current_orphan_count=0 elapsed_ms=42 bronze_orphans_reaped=0 bronze_ttl_gc_deleted=0
```

Non-zero `bronze_orphans_reaped` on the first tick after upgrade is expected if your VM was affected by the 2026-05-24 incident — the reaper is cleaning up an accumulated backlog. Subsequent ticks should report 0.

## Rollback

If something goes wrong, downgrade to `v2026.5.24a4` and revert the `.env` tag:

```bash
# Drop the line written by #313, then re-pull the previous tag:
sed -i '/^KAIRIX_IMAGE_TAG=/d' /opt/kairix/app/.env
KAIRIX_IMAGE_TAG=2026.5.24a4 docker compose pull
KAIRIX_IMAGE_TAG=2026.5.24a4 docker compose up -d --force-recreate
```

Rolling back leaves any bronze blobs that were reaped in the orphan sweep gone — they were unreferenced garbage either way. The `bronze_ttl_gc` flag drops to `False` automatically on the older code.
