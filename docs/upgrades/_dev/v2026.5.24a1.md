# Upgrading to kairix v2026.5.24a1 (alpha)

This is the production alpha for the topology operator-config surface plus the SharePoint connector. Existing deployments don't need to change anything to pull this version — every new behaviour sits behind a default-off feature flag. Flip the flags only when you've read the cutover section below.

## What this release covers

- **MCP cold-start is no longer an adoption blocker.** The HTTP MCP server now returns HTTP 503 with `Retry-After` while the search pipeline is warming, and the `/healthz/ready` endpoint is the single source of truth for readiness. Structured startup logs ship the warm-up event so you can grep for the readiness transition in your log shipper.
- **The new topology operator-config surface lands behind `topology_config`.** A new `topology:` block in `kairix.config.yaml` declares connectors / credentials / cc_pairs / collections / scope_profiles / skills as first-class operator entities. The block parses + cross-references through `kairix config validate`; the apply-bridge materialises the declared cc_pairs into the SQLite topology tables when you run `kairix worker apply-config`.
- **Obsidian gets per-folder containers behind `topology_obsidian`.** When the flag is on, the Obsidian connector emits one Container per top-level vault folder (each with its own delta cursor) instead of one connector-wide cursor. The hierarchy walk now emits one FOLDER node per directory parent-before-child.
- **The SharePoint connector ships behind `connector_sharepoint`.** Pulls document libraries (PDF / DOCX / PPTX / XLSX) via Microsoft Graph drive-delta query, then dispatches binaries through the existing kairix extractor registry. Reuses the M365 Azure AD app registration the email-headers + calendar siblings already use — one tenant id / client id / client secret triple covers all three connectors.

Three new `kairix onboard check` checks land alongside, each gated by the same flag:

- `topology_config_valid` — parses + cross-references the `topology:` block
- `topology_cc_pairs_registered` — confirms each declared cc_pair has a row in `topology_cc_pairs`
- `sharepoint_credentials_loaded` — confirms the three M365 secrets resolve via `kairix.secrets.get_secret`

When the corresponding flag is off, each new check reports `ok=true` with a `"skipped — <flag> flag is OFF"` detail. Default-safe: a fresh install sees 14 checks pass (was 11), no operator action required.

## Before the upgrade

Capture your baseline so you can compare after pulling.

1. **Back up your data volumes.** Docker: `docker run --rm -v kairix-data:/data -v "$PWD":/backup busybox tar czf /backup/kairix-data-pre-v2026.5.24a1.tgz /data`. Pip: copy `~/.cache/kairix/index.sqlite` and your document root to a snapshot dir.
2. **Snapshot your eval baseline.** Run `kairix benchmark run reflib --out benchmark-results/pre-v2026.5.24a1.json` and keep the file. After the upgrade, run again with the same flags and diff with `--baseline benchmark-results/pre-v2026.5.24a1.json`.
3. **Note the current `kairix onboard check --json` envelope** so you can confirm nothing regresses. New deployments should expect three new check entries (each reporting `skipped` with the flag off).

## After the upgrade — opting into topology + SharePoint

Everything below is OPTIONAL. Skip this section if you're not running the alpha.

### 1. Add the `topology:` block

Copy [`kairix.config.example.yaml`](https://github.com/three-cubes/kairix/blob/main/kairix.config.example.yaml) and paste the `topology:` block into your `kairix.config.local.yaml` (Docker overlay) or `kairix.config.yaml` (pip). Edit the connector ids, credential names, cc_pair names, and scope_profile actor_ids to match your deployment.

### 2. Set the SharePoint secrets (only if enabling `connector_sharepoint`)

**Required privileges** — grant in Azure Portal → App registrations → your app → **API Permissions** → Add Permission → Microsoft Graph → **Application Permissions**:

| Permission | Why |
|---|---|
| `Sites.Read.All` | Enumerate accessible sites + their drives |
| `Files.Read.All` | Read file content from any drive the app has site access to |

Both are tenant-wide application permissions and require **admin consent** in the portal after they're added (click "Grant admin consent for your-tenant"). The connector calls `GET /sites?search=*`, `GET /sites/{id}/drives`, `GET /drives/{id}/root/delta`, and `GET /drives/{id}/items/{id}/content` — no per-site or per-drive sharing step is needed once admin consent is granted.

If you already run the M365 email-headers or calendar connector, the same app registration covers SharePoint too — add the two permissions above to the existing app rather than registering a second one.

Provision the three secret values. **Use whichever path your deployment already uses** — see [`docs/getting-started/agent-driven-setup.md §3 "Secrets shape"`](../getting-started/agent-driven-setup.md#3-secrets-shape) for the full secrets reference.

| Path | Where each secret goes |
|---|---|
| Azure Key Vault | Create secrets in your vault with the names `connector-m365-tenant-id`, `connector-m365-client-id`, `connector-m365-client-secret` (the names are the lowercase-hyphenated logical names verbatim). Make sure the kairix runtime principal has `Get` permission on the vault. |
| Bundle env file (`/run/secrets/kairix.env` Docker / `~/.config/kairix/secrets/kairix.env` pip) | `CONNECTOR_M365_TENANT_ID=<value>` etc. — the env-var-name form is the upper-snake-case version of the logical name. |

### 3. Flip the flags

In your `kairix.config.yaml`:

```yaml
features:
  topology_config: true        # parse + apply the topology block
  topology_obsidian: true      # per-folder containers (Obsidian only)
  connector_sharepoint: true      # enable the SharePoint connector
  # topology_runtime: true     # opt in only AFTER the above three soak — see "Cutover" below
```

Or via env (overrides config):

```
KAIRIX_FEATURE_TOPOLOGY_CONFIG=true
KAIRIX_FEATURE_TOPOLOGY_OBSIDIAN=true
KAIRIX_FEATURE_CONNECTOR_SHAREPOINT=true
```

### 4. Apply + verify

```bash
kairix worker apply-config         # materialise declared cc_pairs into topology_cc_pairs
kairix config validate             # parser + 5 cross-reference checks
kairix features status             # confirm the flags are on
kairix onboard check               # 14/14 should pass; the 3 new checks must now exercise live paths
```

If `kairix onboard check` fails, every failure now ships with a one-line `remediation` string — read the `detail` + `remediation` to see the exact next command.

### Cutover protocol for `topology_runtime`

This flag changes chunk write routing — it sends writes through the per-cc_pair `CollectionRouter` instead of the legacy single-collection writer. Do NOT flip it on a soaked corpus without following the cutover protocol in [`docs/architecture/feature-flag-architecture.md`](../architecture/feature-flag-architecture.md):

1. Run `python3 scripts/cutover/capture_baseline.py` to snapshot pre-flip state digest + eval scores + probe latency.
2. Flip the flag (config or env).
3. Soak for 24+ hours.
4. Run `python3 scripts/cutover/capture_baseline.py` again post-flip.
5. Run `python3 scripts/cutover/diff_baseline.py` and confirm: state delta within ±2%, eval within ±2pp, latency within ±20%, sample-journey ≥80% parity.

If any gate fails, flip the flag back to false and revert.

## Expected drift

- **reflib NDCG@10 may dip 0.01–0.02** if you flipped `connector_sharepoint` and pointed it at a real SharePoint corpus. The new corpus shifts the cross-collection ranking; absolute scores against the bundled gold suite are unaffected, but if your custom gold suite mixes Obsidian + SharePoint queries the relative weight changes. Re-run `kairix benchmark run` after a full embed pass to settle the new baseline. This drift closes when KFEAT-015 ships per-collection ranker calibration.
- **First Obsidian sync after flipping `topology_obsidian` re-walks every folder** to emit the per-folder containers. Subsequent syncs ride the delta cursors and are fast.
- **MCP cold-start time is unchanged** but now machine-readable. Any agent or healthcheck that polled `/healthz/ready` keeps working; agents that previously parsed the cold-start envelope from tool responses can now poll the HTTP endpoint instead.

## Rolling back

Every new behaviour is reversible by removing the flag entry from your `features:` block (or unsetting the `KAIRIX_FEATURE_*` env var). The `topology:` YAML block stays parseable when the flag is off — it just becomes inert. No data migration is required to roll back; the `topology_cc_pairs` rows the apply-bridge wrote are read-only inputs to the runtime, not authoritative state.

If you've flipped `topology_runtime`, the rollback requires re-running `kairix worker apply-config` against the legacy single-collection layout. See the cutover protocol above.

## Things that haven't changed

- The legacy `collections:` + `agents:` blocks at the top level of `kairix.config.yaml`. Existing operators continue to use them; the new `topology:` block is an opt-in alternative, not a replacement.
- The provider plugin selector (`provider:`). Same shape, same plugins.
- MCP tool names + JSON schemas. The 12 tools shipped in v2026.5.18 (including `warm`) are unchanged.
- Authentication. kairix continues to have no built-in auth; deployments that put a gateway in front stay unchanged.
