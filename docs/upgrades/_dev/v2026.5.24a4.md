# Upgrading to kairix v2026.5.24a4 (alpha)

This is a small additive follow-up to `v2026.5.24a3`. The single user-visible change is per-drive folder filtering for the SharePoint connector — operators pointing at a drive that mixes "worth indexing" and "skip this" content can now scope by top-level folder instead of either ingesting everything or moving content around in SharePoint.

If you're already on `v2026.5.24a3` and don't have a SharePoint connector configured, this upgrade is a straight pull with no behaviour change. The default (empty include/exclude) preserves prior whole-drive walks bit-for-bit.

## What this release covers

- **`include_paths` and `exclude_paths` on each SharePoint drive entry.** Two new optional lists per drive in `kairix.config.yaml`. Empty = whole drive walked (current behaviour). Non-empty `include_paths` = only items whose path starts with one of the listed paths land as change events. `exclude_paths` = drop matching items even when an include matched. Segment-boundary prefix match (`/Curated-Content` matches `/Curated-Content/foo.md` but not `/Curated-Content-Backup/foo.md`), case-insensitive.
- **Startup probe for missing folders.** When you set `include_paths`, the connector calls Graph once per path at startup to confirm the folder exists. A 404 surfaces as a `sharepoint_probe_missing_folder` warning — the connector continues syncing the present paths so a typo doesn't silently drop your data.
- **Parse-time refusal of exact include/exclude overlap.** If you accidentally put the same path in both lists (`include_paths: ["/Foo"]` + `exclude_paths: ["/Foo"]`), `kairix config validate` and `kairix worker apply-config` refuse with a one-line fix pointer. Strict children (e.g. include `/Foo` + exclude `/Foo/draft`) are the intended use case and remain legal.
- **Auto-synthesised cc_pair labels** for drives that have a filter but no operator-supplied `display_name`. Two cc_pairs against the same drive with different `include_paths` now surface as `"<short-drive-id> [/Curated-Content]"` and `"<short-drive-id> [/Engineering]"` in `kairix features status`, `tool_features_status`, and the structured log envelopes — instead of two identical opaque drive ids.

## After the upgrade — scoping a SharePoint drive (optional)

Skip this section unless you want to filter a SharePoint drive by folder.

### Pick which folders to index

Until `kairix sharepoint discover` lands (KFEAT-022, design landed in `docs/architecture/guided-configuration.md`), enumerate the drive's top-level folders manually:

```bash
# Get a Graph access token using your existing M365 secrets
TENANT=$(az keyvault secret show --vault-name $KAIRIX_KV_NAME --name connector-m365-tenant-id --query value -o tsv)
CLIENT=$(az keyvault secret show --vault-name $KAIRIX_KV_NAME --name connector-m365-client-id --query value -o tsv)
SECRET=$(az keyvault secret show --vault-name $KAIRIX_KV_NAME --name connector-m365-client-secret --query value -o tsv)
TOKEN=$(curl -sS -X POST "https://login.microsoftonline.com/$TENANT/oauth2/v2.0/token" \
  -d "client_id=$CLIENT&client_secret=$SECRET&scope=https%3A%2F%2Fgraph.microsoft.com%2F.default&grant_type=client_credentials" \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['access_token'])")

# List sites
curl -sS -H "Authorization: Bearer $TOKEN" 'https://graph.microsoft.com/v1.0/sites?search=*' | jq '.value[] | {name: .displayName, id, web: .webUrl}'

# For a chosen site, list its drives
curl -sS -H "Authorization: Bearer $TOKEN" "https://graph.microsoft.com/v1.0/sites/<site-id>/drives" | jq '.value[] | {name, id}'

# For a chosen drive, list its top-level folders
curl -sS -H "Authorization: Bearer $TOKEN" "https://graph.microsoft.com/v1.0/drives/<drive-id>/root/children" | jq '.value[] | {name, size, folder: .folder.childCount}'
```

### Update `kairix.config.yaml`

```yaml
topology:
  connectors:
    - id: sharepoint-curated-conn
      kind: sharepoint
      default_sensitivity: internal
      connector_specific_config:
        drives:
          - drive_id: "b!a0rph..."
            site_id: "yourtenant.sharepoint.com,site-guid,web-guid"
            include_paths:
              - "/Curated-Content"
              - "/Shared Documents"
            exclude_paths:
              - "/Curated-Content/draft"
```

Then apply + verify:

```bash
kairix worker apply-config       # materialise the cc_pair
kairix config validate           # check parse + cross-references
kairix worker run                # start indexing — only the included folders
```

Watch the worker logs for `sharepoint_probe_missing_folder` warnings — if any include_paths don't exist in the drive, fix the YAML before the first sync completes.

## Expected drift

- **NDCG changes scale with the filtered subset.** Ingesting only `/Curated-Content` instead of the whole drive shifts the document count, which shifts the cross-collection ranking. Re-run `kairix benchmark run` after the first full embed pass and re-baseline.
- **First sync still walks the full delta stream.** The filter is client-side post-processing — Graph's delta endpoint doesn't take a path filter, so the connector pays the listing cost for the whole drive even when most items are dropped. On a 126 GB drive with a 3 GB include, the first delta walk takes the same wall time as an unfiltered walk; only the extract + embed + index work is reduced. Per-folder delta optimisation is a future enhancement noted in the design doc.

## Rolling back

Remove the `include_paths` / `exclude_paths` entries from your `kairix.config.yaml`. The connector returns to whole-drive walks on the next tick.

## Things that haven't changed

- The Graph API permissions you grant. `Sites.Read.All` + `Files.Read.All` still cover this. The filter is a kairix-side scope, not a Graph-side scope. (For tenant-level scope reduction, look at Microsoft's `Sites.Selected` permission model.)
- The cursor format. Filter is a per-tick view, not persisted state — operators can change `include_paths` without invalidating the per-drive deltaLink.
- Every other connector. Slack, GitHub, Notion, and the existing M365 + Obsidian + Dex connectors are unchanged. Path-filter generalisation to those connectors is part of KFEAT-022.
