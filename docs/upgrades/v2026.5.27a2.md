## Upgrading to kairix v2026.5.27a2 (alpha)

Urgent dogfood fix. v2026.5.27a1 deployed the markitdown converter extras (#322) and the `kairix worker reextract` recovery tool (Bug D), but the SharePoint reextract surfaced a disk-space cascade nobody had seen yet: one pathological PPTX expanded to fill the 2GB tmpfs at `/tmp`, every subsequent extraction failed at the `tmp.write()` step, AND each of those failures leaked the empty tmpfile placeholder. Over a single reextract attempt 8,090 of 8,396 items dead-lettered with `[Errno 28] No space left on device` and 8,087 zero-byte stubs accumulated in `/tmp`.

Two fixes ship together so the cascade can't recur:

1. **The leak is sealed** — the markitdown extractor's `write_bytes()` step now lives inside the try/finally that unlinks the tmpfile, so a write failure no longer orphans the empty placeholder.

2. **The scratch dir moves off tmpfs** — `TMPDIR=/data/kairix/tmp` ships in the image, routing Python's `tempfile` onto the bind-mounted runtime disk (tens of GB available) instead of the 2GB tmpfs. A single pathological extraction can no longer exhaust capacity.

Together they remove both legs of the cascade: even if a single file is genuinely huge (legitimate-but-extreme), it can't fill the scratch dir; and if it does still fail, the cleanup discipline prevents a snowball of leaked placeholders.

## What this release covers

- **`kairix/extractors/markitdown/extractor.py` cleanup discipline.** `tmp_path.write_bytes(raw)` moved INSIDE the try block whose finally calls `tmp_path.unlink()`. Pre-fix the write was inside the `with tempfile.NamedTemporaryFile(delete=False) as tmp:` block but OUTSIDE the try/finally — a write failure left the empty placeholder on disk. New regression cover: a structural source-string assertion locks the line order so a future refactor that re-inverts the shape trips a clear message naming this incident. Plus a `scratch_dir` constructor kwarg as the F6 DI seam so cleanup tests don't need to monkeypatch the tempfile stdlib.

- **Dockerfile installs `[ocr]` extra + `tesseract-ocr` system binary.** Closes the `extractor_libraries_importable` onboard check that went unhealthy on the v2026.5.27a1 deploy. The OCR extractor's Python libraries (`pytesseract`, `opencv-python-headless`, `Pillow`, `pdfplumber`) are now in the image; pytesseract wraps a C++ engine that needs `apt install tesseract-ocr` separately. Pre-arms the next phase of #23 (wiring the OCR fallback through the escalation chain).

- **`TMPDIR=/data/kairix/tmp` in the image.** Python's `tempfile` honours this env var; every extractor's tempfile now lands on the bind-mounted runtime volume instead of the 2GB tmpfs at `/tmp`. The 2GB `/tmp` tmpfs from #317 stays in compose for general OS scratch but kairix no longer fights for that 2GB.

- **`EscalatingExtractor` framework class** (`kairix.core.connectors.escalation`). First piece of #23. Wraps an ordered list of `Extractor` instances and walks the chain via `quality_ok` — when the first member returns `quality_ok=False` (e.g. markitdown on an image-only PDF), the chain falls through to the next tier (e.g. pdf_fallback, then ocr). Returns the first member whose output is good enough. Exhaustion surfaces the longest-markdown attempt with a `trace.exhausted=True` marker. Exceptions in one tier don't kill the chain. The wiring into `_run_one_connector_batch` / `_build_reextract_components` (via `extractor_chain: [...]` opt-in config) lands in a later release with BDD + F30 outcome tests.

## Before the upgrade

If your `/tmp` tmpfs has accumulated leaked stubs from v2026.5.27a1, clear them before deploying:

```bash
docker exec app-kairix-1 find /tmp -mindepth 1 -name 'tmp*' -delete
docker exec app-kairix-worker-1 find /tmp -mindepth 1 -name 'tmp*' -delete
```

(One-time cleanup. The fix prevents recurrence but does not retroactively clean pre-fix tmpfs state.)

## Recovering dead-lettered items after the upgrade

Once the new image is live and scratch is disk-backed, the reextract from Bug D should clear most of the disk-space-failed items:

```bash
# Pause the worker so the reextract has the DB lock to itself.
docker compose stop kairix-worker

# Dry-run first to size the recovery.
docker compose exec kairix kairix worker reextract --source-name sharepoint --dry-run --json

# Run for real once the dry-run looks right.
docker compose exec kairix kairix worker reextract --source-name sharepoint --json

# Restart the worker.
docker compose start kairix-worker
```

Counters in the JSON envelope:

- `recovered` — extract + silver + writer succeeded; dead-letter row cleared.
- `still_failing` — extract or downstream raised again; dead-letter row kept.
- `skipped_no_bronze` — bronze row was pruned (e.g. #318 orphan reaper); operator must re-fetch from source.
- `skipped_no_connector` — `source_name` isn't in current config.

## Rollback

```bash
KAIRIX_IMAGE_TAG=2026.5.27a1 docker compose pull
KAIRIX_IMAGE_TAG=2026.5.27a1 docker compose up -d --force-recreate
```

Rolling back re-introduces the tmpfile leak and the disk-space cascade — only do this if v2026.5.27a2 surfaces a different regression. The chunks written by v2026.5.27a2 silver remain valid; the change here is operational (cleanup + scratch location), not data-format.
