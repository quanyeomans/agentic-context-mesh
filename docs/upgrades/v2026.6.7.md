# Upgrading to kairix v2026.6.7

This guide tells you what to do when upgrading. It is written so an agent or a human can follow it without external context — drop it into your reading list and the upgrade self-manages.

## What this release covers

Two big wins for agents-and-humans using kairix daily:

- **Brief and search drop from ~6 seconds to under one second** when an MCP server is running. The CLI now talks to your warm MCP server instead of starting a fresh Python process every time. Same output, same flags — just much faster.
- **Setup gets a discovery step**. The new `kairix onboard scan` command walks your knowledge store, finds your agents on disk, and proposes a config block you can paste into `kairix.config.yaml`. No more hand-authoring the agents block.

Plus three quality-of-life improvements: `kairix doctor agent` validates your agent setup against what's actually on disk, `kairix caches` now shows the warm MCP server's cache state (not a fresh empty CLI process), and the cold-start envelope is captured in a runbook so operators know what to expect during MCP restarts.

This release also retires the `/memory` subdirectory convention. Each agent now declares its own paths under `agents:` in `kairix.config.yaml`. Out-of-the-box kairix still works without that block — defaults synthesise a sensible scope per agent — but the new explicit shape is what `kairix onboard scan` produces.

## 1. CLI text mode routes through warm MCP

Run `kairix brief shape` from a shell when your MCP server is running. Old behaviour: every invocation spun up the embedding model, opened the vector index, and reconnected to neo4j — ~6 seconds, every time, even when an MCP server was already warm one process away. New behaviour: the CLI checks whether an MCP server is responsive, routes the call through it, and renders byte-identical output from the response.

Same change applies to `kairix search`, `kairix bootstrap`, `kairix prep`, `kairix research`, `kairix contradict`, `kairix timeline`. When MCP is cold or absent, the CLI falls through to the in-process path automatically — no command failures, just slower responses.

The behaviour is controlled by a feature flag (`cli_routes_through_warm_mcp`, on by default). Check status with `kairix features status`.

## 2. Agent setup gets discovery + validation tools

Three new commands:

| Command | What it does |
|---|---|
| `kairix onboard scan` | Walks your knowledge-store root, finds agent-shaped subdirectories, and emits a paste-ready `kairix.config.yaml` `agents:` block. Cross-references workspace folders when present. |
| `kairix onboard agent --name <agent>` | Same discovery, scoped to one agent. Useful when you add a new agent later. |
| `kairix doctor agent --all` | Validates your configured agent scopes against disk: missing paths, empty surfaces, stale files (older than 30 days), ambiguous globs. Exit 0 means everything is healthy. |

Three new MCP tools mirror the CLI so agents can call them programmatically: `onboard_scan`, `onboard_agent`, `doctor_check_all`, `doctor_check_agent`.

Recommended first-time setup:

```bash
# Discover agents on disk
kairix onboard scan --memory-root /path/to/agent-knowledge \
                    --workspace-root /path/to/workspaces \
                    --yaml > agents-block.yaml

# Review the proposal, paste relevant agents into kairix.config.yaml,
# then validate
kairix doctor agent --all
```

The doctor output flags any agent with `warn` or `error` so you see drift before agents do.

## 3. `kairix caches` shows the warm MCP server's state

Old behaviour: running `kairix caches` from a shell started a fresh Python process and showed that process's empty caches (size=0 across the board). Operators saw zeros and concluded the cache feature was broken. New behaviour: the CLI routes through a new `caches_status` MCP tool when an MCP server is responsive. The envelope includes the MCP server's process id and uptime so you can see this is real server-side data:

```json
{
  "caches": [
    {"name": "query_result_cache", "size": 8, "hits": 6, "misses": 3, "hit_rate_pct": 66.7},
    ...
  ],
  "process_pid": 1,
  "process_uptime_s": 206.4
}
```

When MCP is cold or unavailable, the CLI prints a one-line note to stderr ("NOTE: MCP server not responsive — showing in-process cache state for this CLI invocation only.") and falls through to the old in-process collectors.

## 4. Cold-start envelope reference + soak test

Two artefacts:

- **Runbook** at `docs/operations/runbooks/cold-start-envelope-reference.md` — captures real bytes from a production cold-start (HTTP 503, `Retry-After: 8` header, structured body with `KAIRIX_COLD_START` error code, `agent_instruction` containing `next:`/`fix:` markers). When an operator sees this envelope, they have a verbatim reference to compare against.
- **Soak test** at `tests/soak/test_cold_start_envelope_visible_on_restart.py` — spawns MCP, hits a tool while readiness gate is still closed, asserts the envelope shape. Runs nightly in the soak workflow so envelope drift is caught before it reaches operators.

## Configuration migration from v2026.6.6

Most deployments need no config change. The defaults still synthesise a sensible scope per agent.

If you want the new explicit shape (recommended — `kairix doctor agent --all` reports clean only when scopes are explicit):

1. **Add an `agents:` block to `kairix.config.yaml`.** Easiest path: run `kairix onboard scan --memory-root <your-agent-knowledge-root> --yaml > agents.yaml`, review the output, paste relevant agents into your kairix.config.yaml.
2. **Drop `KAIRIX_AGENT_MEMORY_ROOT` from your environment.** No replacement — the `agents:` block (or `agent_defaults` fallback) is the source of truth.
3. **Update any scripts using `kairix brief --memory-root PATH`.** That flag is gone; use the `agents.<name>.surfaces` config instead.

## Retired in this release

- **`agent_memory_path()` Python helper.** The four production callsites now read from `AgentScope` via `kairix.core.agents.scope.get_agent_scope`. Out-of-tree callers (if any) should migrate to the same surface.
- **`KAIRIX_AGENT_MEMORY_ROOT` environment variable.** Replaced by the `agents:` block in `kairix.config.yaml`.
- **`--memory-root` flag on `kairix brief`.** Configure once in `kairix.config.yaml`, not per invocation.

## Known caveats

- The `:main` Docker tag tracks the latest commit on the `main` branch. For pinned-tag deployments, use a `vYYYY.M.D` release tag.
- A warm-state regression has been seen in long-running deployments where the MCP server's "warm" flag flips back to "cold" after several hours of uptime, leaving all requests returning the `KAIRIX_COLD_START` envelope until container restart. Tracked in issue #425; fix planned for the next release. Workaround: `docker compose restart kairix` clears the state and warmup completes again in ~14 seconds.
